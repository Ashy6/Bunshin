# 离线恢复码与密码重置方案

## 1. 结论

离线恢复码适合 Bunshin 这种单管理员、自托管项目，可以作为邮箱不可用时的主要恢复能力。但恢复码不应被设计成“直接登录凭据”，而应作为一次性的密码重置授权。

推荐流程：

```text
首次创建管理员
  → 系统生成 10 个一次性恢复码
  → 只展示一次，允许复制、下载和打印
  → 服务端只保存哈希

忘记密码
  → 选择“使用离线恢复码”
  → 输入管理员邮箱、一个恢复码、新密码、确认密码
  → 服务端验证并消费该恢复码
  → 修改密码
  → 注销全部旧 Session
  → 作废整套旧恢复码
  → 使用新密码登录
  → 在安全设置中重新生成一套恢复码
```

不建议在同一个匿名重置页面中提供“输入新的恢复码”。拿到一个恢复码的人只有一次恢复权限，不应同时获得选择长期恢复凭据的能力。新的恢复码应在成功设置密码并重新登录后生成。

## 2. 为什么不把恢复码当成登录密码

如果恢复码可以直接建立后台 Session，会产生以下问题：

- 用户可能长期重复使用同一个恢复码，失去“一次性”属性。
- 无法强制管理员更新已经泄露或遗忘的密码。
- 登录日志难以区分正常登录与账户恢复。
- 攻击者拿到恢复码后可以立即进入后台，而不是被限制在单一的密码重置动作。

因此恢复码只能调用密码重置接口。重置成功后，用户仍需要使用新密码走正常登录流程。

## 3. 恢复码格式

默认生成 10 个一次性恢复码，推荐格式：

```text
BNSH-7K3M-Q9TX-4P2R
```

规则：

- 使用密码学安全随机数生成器 `crypto.getRandomValues`。
- 去掉容易混淆的字符，例如 `0/O`、`1/I/L`。
- 每个恢复码至少包含约 80 bit 随机熵。
- 显示时使用分段格式，提交前服务端统一移除空格和连字符并转为大写。
- 每个恢复码只能成功使用一次。

恢复码不是验证码，不采用 6 位数字。6 位数字只有约一百万种组合，不适合作为长期离线凭据。

## 4. 是否允许用户自定义恢复码

默认不推荐。用户自定义内容容易复用旧密码、姓名、生日或常见短语，安全性远低于随机恢复码。

如果产品仍希望提供自定义能力，应把它命名为“自定义恢复短语”，并满足：

- 至少 24 个字符。
- 必须同时包含多个单词或由密码管理器生成。
- 不得与当前密码相同。
- 只能在已登录且近期重新验证密码后设置。
- 页面明确提示随机恢复码更安全。
- 自定义恢复短语只能有一个，使用后立即作废。
- 服务端使用与密码相同或更强的慢哈希，而不是普通 SHA-256。

推荐第一版只实现系统随机恢复码。自定义恢复短语作为后续可选增强，不应成为默认路径。

## 5. 存储设计

服务端绝不保存恢复码明文。D1 只保存不可逆哈希和使用状态。

建议新增表：

```sql
CREATE TABLE admin_recovery_codes (
  id TEXT PRIMARY KEY,
  admin_id TEXT NOT NULL,
  code_hash TEXT NOT NULL UNIQUE,
  batch_id TEXT NOT NULL,
  used_at TEXT,
  created_at TEXT NOT NULL,
  expires_at TEXT
);

CREATE INDEX idx_recovery_codes_admin
  ON admin_recovery_codes(admin_id, created_at);
```

哈希建议：

```text
SHA-256(normalizedRecoveryCode + SESSION_SECRET)
```

随机恢复码本身具有足够熵，因此可以使用带服务端 Pepper 的 SHA-256。自定义恢复短语熵不可控，必须使用 PBKDF2、scrypt 或 Argon2 等慢哈希。

`SESSION_SECRET` 只保存在 Worker Secret 中。数据库泄露时，攻击者无法直接离线枚举恢复码。

## 6. 首次创建管理员

管理员 bootstrap 成功后：

1. 生成一批 10 个恢复码。
2. 将哈希批量写入 D1。
3. 在浏览器中只显示一次明文。
4. 提供“复制全部”“下载 TXT”“打印”三个操作。
5. 要求用户确认“我已经保存恢复码”后再进入后台。

恢复码不能再次从服务器读取。若用户没有保存，只能在已登录状态下重新生成，生成新批次时必须作废全部旧批次。

开源部署脚本可以额外生成一份部署者应急恢复材料，但不得写入 Git、日志或构建产物。

## 7. 忘记密码页面

登录页提供：

```text
忘记密码？
  ├─ 使用离线恢复码
  └─ 使用邮箱验证码（仅邮件服务已配置时展示）
```

离线恢复码表单字段：

- 管理员邮箱。
- 离线恢复码。
- 新密码。
- 确认新密码。

不在该表单中设置新恢复码。重置成功后显示：

> 密码已修改，全部旧会话和旧恢复码已失效。请使用新密码登录，并立即在“系统设置 → 账户安全”中生成新的离线恢复码。

## 8. 服务端重置流程

推荐接口：

```text
POST /api/admin/auth/recovery/reset
```

请求体：

```json
{
  "email": "admin@example.com",
  "recoveryCode": "BNSH-7K3M-Q9TX-4P2R",
  "password": "new strong password"
}
```

服务端处理顺序：

1. 规范化邮箱和恢复码。
2. 执行来源 IP 与邮箱组合限流。
3. 查询管理员与未使用的恢复码哈希。
4. 使用常量时间逻辑比较哈希。
5. 验证新密码至少 12 位，并禁止与旧密码相同。
6. 在同一 D1 batch 中更新密码、消费恢复码、作废同批次其他恢复码、删除全部 Session。
7. 写入脱敏审计事件 `password_reset_by_recovery_code`。
8. 返回成功，但不自动创建 Session。

数据库操作应采用条件更新，例如 `used_at IS NULL`，防止同一个恢复码被两个并发请求重复消费。

## 9. 限流与防枚举

建议限制：

- 同一“来源 IP + 邮箱”15 分钟最多尝试 5 次。
- 同一恢复码连续失败后增加退避时间。
- 返回统一错误：“恢复码无效、已使用或已过期”。
- 不向匿名调用者暴露邮箱是否存在、剩余恢复码数量或具体失败原因。
- 成功恢复后向生产监控写入安全事件。
- 如果邮件服务可用，成功恢复后向管理员邮箱发送安全通知，但通知不包含新密码或恢复码。

恢复页面可在 Turnstile 配置完成后增加人机验证，但 Turnstile 不能替代服务端限流。

## 10. 已登录状态下的账户安全页面

建议在“系统设置 → 账户安全”增加：

- 当前管理员邮箱。
- 修改密码。
- 恢复码状态：剩余数量、生成时间，不显示明文。
- 重新生成恢复码。
- 下载新恢复码。
- 注销其他设备。
- 邮箱验证码服务状态。

重新生成恢复码属于敏感操作，必须要求输入当前密码。若未来启用 MFA，还应要求 TOTP。

## 11. 丢失所有凭据时怎么办

如果管理员同时丢失：

- 当前密码；
- 全部恢复码；
- 邮箱验证能力；

则只能由 Cloudflare/D1 的部署所有者执行应急重置。这是自托管系统的最终信任根，不应提供无需部署权限的万能后门。

仓库可以提供交互式命令：

```bash
pnpm admin:reset-password
```

命令在本地隐藏输入新密码，生成哈希后更新远程 D1，并注销全部 Session。密码不能作为命令行参数，避免进入 shell history 和进程列表。

## 12. 与邮箱验证码方案的关系

两种方式互为补充：

| 方式 | 依赖 | 适用情况 |
| --- | --- | --- |
| 离线恢复码 | 用户保存的恢复材料 | 邮件不可用、域名故障、快速应急 |
| 邮箱验证码 | 邮件服务和管理员邮箱 | 日常自助找回 |
| 部署者 CLI | Cloudflare/D1 部署权限 | 所有普通恢复方式均丢失 |

第一阶段优先实现随机离线恢复码和部署者 CLI。自定义恢复短语、邮箱安全通知与 TOTP 可以在后续增强。

## 13. 验收标准

1. 初始化时生成 10 个恢复码且只显示一次。
2. D1 中不存在任何恢复码明文。
3. 正确恢复码可以修改密码，但不能直接登录。
4. 使用后该恢复码和同批次其他恢复码全部失效。
5. 所有旧 Session 被删除。
6. 重复使用、并发使用、错误邮箱和错误恢复码均失败。
7. 失败响应不能判断管理员邮箱是否存在。
8. 限流达到阈值后不再执行密码哈希和数据库敏感操作。
9. 登录后可以重新生成并下载新的一批恢复码。
10. Git、Worker 日志、审计日志和监控中均不出现恢复码明文。
